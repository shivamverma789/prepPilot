1. INTRODUCTION
================================================================

1.1 PURPOSE

This Software Design Specification (SDS) document describes the
complete analysis and design of PrepPilot — an AI-powered placement
preparation web platform for engineering students. The purpose of
this document is to provide a detailed technical blueprint of the
system including its architecture, data models, component structure,
and user interface design.

This document serves as the primary reference for understanding how
the system is structured, how its components interact, and how the
database is organized. It bridges the gap between the requirements
specification and the actual implementation.

- Bold text indicates important terms or section headings
- [DIAGRAM REQUIRED] markers indicate where actual diagrams must
  be inserted by the student

2. ANALYSIS MODEL
================================================================

2.1 METHODOLOGY USED

PrepPilot follows the Object-Oriented Analysis and Design (OOAD)
methodology. The system is modeled using UML (Unified Modeling
Language) diagrams to represent the structure and behavior of the
application.

Key OO principles applied:
- Encapsulation: Each module (auth, roadmap, resume, assessment,
  activity) is encapsulated in its own controller and service files
- Abstraction: The AI client (aiClient.js) abstracts all Gemini API
  interactions behind a single generateText() method
- Modularity: Routes, controllers, models, services, and views are
  strictly separated following MVC pattern
- Reusability: The AI client, email service, and text extractor are
  shared services used across multiple features

Development followed an iterative approach:
- Iteration 1: Authentication + Onboarding
- Iteration 2: Roadmap Generation + Dashboard
- Iteration 3: Resume Analysis + Resume Builder
- Iteration 4: Assessment + Activity Tracker
- Iteration 5: Interview Prep + Deployment

USE CASE SPECIFICATIONS (KEY USE CASES):
------------------------------------------------------------------

USE CASE: UC06 — Complete Onboarding
Actor: Student
Precondition: User is registered and email is verified
Main Flow:
  1. User navigates to /onboarding
  2. Step 1: User enters career goals (from suggestions or custom)
     and selects target company type
  3. Step 2: User enters academic details (year, degree, branch,
     university)
  4. Step 3: User adds technical skills with proficiency levels
     (beginner/intermediate/advanced) and exposure levels
  5. Step 4: User describes experience (projects count, internship,
     daily study hours, resume readiness)
  6. System saves profile to users collection in MongoDB
  7. System redirects to dashboard
Postcondition: User profile is complete; roadmap can be generated
Alternate Flow: If user skips required fields, validation error shown

USE CASE: UC08 — Generate AI Roadmap
Actor: Student
Precondition: Onboarding is complete
Main Flow:
  1. User clicks "Generate Roadmap" on dashboard
  2. System reads user profile from MongoDB
  3. System builds structured prompt with user profile data
  4. System sends prompt to Google Gemini API
  5. Gemini returns JSON array of phases with skills/subtopics
  6. System parses and validates JSON response
  7. System stores roadmap in roadmaps collection
  8. System renders roadmap on dashboard
Postcondition: Personalized roadmap is displayed
Alternate Flow: If Gemini returns error, retry up to 3 times;
               if all retries fail, show error message

USE CASE: UC11 — Upload Resume for Analysis
Actor: Student
Precondition: User is logged in
Main Flow:
  1. User navigates to /resume
  2. User uploads PDF or DOCX file
  3. Multer middleware stores file in memory buffer
  4. System detects file type (PDF/DOCX)
  5. pdf-parse or mammoth extracts raw text
  6. System sends text to Gemini with ATS scoring prompt
  7. Gemini returns JSON with score, breakdown, issues, suggestions
  8. System renders results page with visual score breakdown
Postcondition: ATS analysis results displayed to user
Alternate Flow: If file is invalid format, show error message

USE CASE: UC18 — Take Skill Assessment Quiz
Actor: Student
Precondition: User has a roadmap with subtopics
Main Flow:
  1. User clicks on a subtopic in their roadmap
  2. System sends subtopic title, skill title, user level to Gemini
  3. Gemini returns 5 MCQ questions in JSON format
  4. System renders quiz with 4 options per question
  5. User selects answers and submits
  6. System scores answers and displays results with explanations
Postcondition: Quiz score and explanations shown; progress tracked
Alternate Flow: If AI fails to generate quiz, show error message

2.4 SEQUENCE DIAGRAM
================================================================

SEQUENCE: Roadmap Generation

Student -> Browser: Click "Generate Roadmap"
Browser -> Express Server (roadmapController): GET /roadmap/generate
Express Server -> MongoDB (userModel): findOne({ _id: userId })
MongoDB -> Express Server: returns user profile document
Express Server -> roadmapAI.js: generatePersonalizedRoadmap(user)
roadmapAI.js -> aiClient.js: generateText(prompt)
aiClient.js -> Google Gemini API: POST /models/generate (with prompt)
Google Gemini API -> aiClient.js: returns raw JSON text
aiClient.js -> roadmapAI.js: returns cleaned JSON string
roadmapAI.js -> roadmapAI.js: JSON.parse(cleaned)
roadmapAI.js -> Express Server: returns phases array
Express Server -> MongoDB (roadmapModel): save(roadmap)
MongoDB -> Express Server: save confirmed
Express Server -> Browser: res.render("dashboard/roadmap", {roadmap})
Browser -> Student: Displays personalized roadmap

------------------------------------------------------------------
SEQUENCE: Resume Analysis

Student -> Browser: Upload PDF file
Browser -> Express Server (resumeController): POST /resume/analyze
Express Server -> multer middleware: store file in memory buffer
multer -> Express Server: req.file.buffer available
Express Server -> textExtractor.js: extractText(buffer, mimetype)
textExtractor.js -> pdf-parse: parse(buffer) [if PDF]
pdf-parse -> textExtractor.js: returns raw text string
textExtractor.js -> Express Server: returns resumeText
Express Server -> resumeAI.js: analyze(resumeText)
resumeAI.js -> aiClient.js: generateText(prompt, {temp:0.2})
aiClient.js -> Google Gemini API: POST /models/generate
Google Gemini API -> aiClient.js: returns JSON analysis
aiClient.js -> resumeAI.js: returns raw response
resumeAI.js -> Express Server: returns parsed analysis object
Express Server -> MongoDB (resumeModel): save(analysis)
Express Server -> Browser: res.render("resume/result", {analysis})
Browser -> Student: Displays ATS score and analysis

3.1 ARCHITECTURAL DESIGN

3.1.1 SYSTEM ARCHITECTURE DIAGRAM

PrepPilot follows a 3-tier web application architecture:

TIER 1 — PRESENTATION LAYER (Client)
  - Web Browser (Chrome, Firefox, Safari, Edge)
  - Renders server-side HTML from EJS templates
  - Sends HTTP requests to Express server
  - Handles minimal client-side JS (autocomplete, form validation)

TIER 2 — APPLICATION LAYER (Server — Render Cloud)
  - Node.js v20 runtime
  - Express.js v5 web framework
  - MVC pattern:
    * Routes: Define URL endpoints
    * Controllers: Handle request/response logic
    * Services: Business logic and AI integration
  - Passport.js: Authentication middleware
  - Multer: File upload handling
  - Puppeteer: PDF generation

TIER 3 — DATA LAYER
  - MongoDB Atlas (cloud database)
  - Mongoose ODM (schema + query layer)
  - connect-mongo (session storage)

EXTERNAL SERVICES:
  - Google Gemini API (AI content generation)
  - Google OAuth 2.0 (social login)
  - GitHub OAuth (social login)
  - Brevo SMTP (email service)
  - LeetCode / Codeforces / CodeChef / HackerRank / GitHub APIs
  - LiveKit (real-time interview application)

3.1.2 DESCRIPTION OF ARCHITECTURAL DESIGN

The application uses the Model-View-Controller (MVC) pattern:

MODEL LAYER:
All data models are defined using Mongoose schemas in the /models
directory. Each model corresponds to a MongoDB collection:
- userModel.js → users collection
- roadmapModel.js → roadmaps collection
- resumeModel.js → resumes collection (analysis + builder)
- assessmentModel.js → assessments collection
- activityModel.js → activities collection
- taskModel.js → tasks collection

VIEW LAYER:
All views are EJS templates in the /views directory, organized by
feature. EJS allows embedding JavaScript logic directly in HTML
for dynamic content rendering. No client-side framework is used —
all rendering is server-side for simplicity and SEO.

CONTROLLER LAYER:
Controllers in /controllers handle HTTP requests, call services,
interact with models, and render views. Each controller is scoped
to one feature domain (auth, roadmap, resume, assessment, etc.).

SERVICE LAYER:
The /services directory contains business logic separated from
controllers:
- services/ai/ — All Gemini AI prompts and response parsing
- services/activity/ — Per-platform coding stats fetchers
- services/parser/ — PDF/DOCX text extraction
- services/emailService.js — Email sending

ROUTING:
All routes are defined in /routes and mounted in app.js with
feature-based prefixes:
- / → authRoutes (login, register, OAuth)
- /onboarding → onboardingRoutes
- /builder → resumeBuilderRoutes
- /resume → resumeRoutes
- /activity → activityRoutes
- /api/interview → interviewRoutes

MIDDLEWARE:
- profileCheck.js: Guards protected routes; redirects to /login
  if not authenticated or to /onboarding if profile incomplete
- Passport.js: Handles session-based authentication
- Multer: Handles multipart/form-data file uploads
- method-override: Enables PUT/DELETE from HTML forms
- cors: Enables cross-origin requests from LiveKit app

3.2.2 NORMALIZATION

MongoDB is a NoSQL document database and does not follow traditional
relational normalization (1NF, 2NF, 3NF). However, the schema design
follows equivalent NoSQL best practices:

Design Decisions:
1. Embedding vs Referencing:
   - Skills, phases, subtopics, sections are EMBEDDED within their
     parent documents because they are always accessed together
     (no need for separate queries)
   - userId is a REFERENCE (foreign key equivalent) in roadmaps,
     resumes, assessments, activities because these are large
     documents accessed independently

2. Data Redundancy:
   - Minimal redundancy — user profile data is stored once in users
     collection and referenced by userId in other collections
   - AI cache in resumebuilder stores computed results to avoid
     re-calling the expensive Gemini API on every page load

3. Equivalent Normal Forms in NoSQL:
   - 1NF equivalent: Each field contains atomic values; arrays are
     used for multi-valued attributes (skills[], careerGoals[])
   - 2NF equivalent: All non-key fields depend on the document's
     primary _id; no partial dependencies
   - 3NF equivalent: No transitive dependencies; userId references
     the users collection rather than duplicating user data

APPENDIX C1: GLOSSARY
================================================================

ATS (Applicant Tracking System):
  Software used by employers to filter and rank resumes based on
  keywords, formatting, and relevance to job descriptions.

API (Application Programming Interface):
  A set of protocols and tools that allows different software
  applications to communicate with each other.

bcrypt:
  A password hashing function designed to be computationally
  expensive, making brute-force attacks impractical.

CORS (Cross-Origin Resource Sharing):
  A browser security mechanism that controls how web pages can
  request resources from a different domain.

EJS (Embedded JavaScript):
  A server-side templating engine that generates HTML markup with
  plain JavaScript embedded within the template.

Express.js:
  A minimal and flexible Node.js web application framework that
  provides routing, middleware, and HTTP utility methods.

Gemini API:
  Google's large language model API used for generating AI content
  including roadmaps, quiz questions, and resume analysis.

JWT (JSON Web Token):
  A compact, URL-safe token format used for securely transmitting
  information between parties (not used in PrepPilot; sessions used).

LiveKit:
  An open-source platform for building real-time audio/video
  applications, used for the mock interview feature.

Mongoose:
  An Object Document Mapper (ODM) for MongoDB and Node.js that
  provides schema-based data modeling.

MongoDB Atlas:
  A fully managed cloud database service for MongoDB, providing
  automated backups, scaling, and monitoring.

Multer:
  A Node.js middleware for handling multipart/form-data, primarily
  used for file uploads.

MVC (Model-View-Controller):
  A software architectural pattern that separates application logic
  into three components: Model (data), View (UI), Controller (logic).

OAuth 2.0:
  An authorization framework that enables third-party applications
  to obtain limited access to user accounts on an HTTP service.

ODM (Object Document Mapper):
  A programming technique for converting data between incompatible
  type systems in object-oriented programming languages and NoSQL
  databases.

Passport.js:
  An authentication middleware for Node.js that supports multiple
  authentication strategies including local, Google, and GitHub.

Prompt Engineering:
  The practice of designing and optimizing input prompts to AI
  language models to produce desired, structured outputs.

Puppeteer:
  A Node.js library that provides a high-level API to control
  headless Chrome/Chromium for PDF generation and web scraping.

Render:
  A cloud platform-as-a-service (PaaS) used to deploy and host
  the PrepPilot web application.

Session:
  A server-side mechanism to persist user state across multiple
  HTTP requests, stored in MongoDB via connect-mongo.

UML (Unified Modeling Language):
  A standardized modeling language used to visualize the design
  of software systems through various diagram types.
